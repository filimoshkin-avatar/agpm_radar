# ADR-0014: Поиск живёт в приложении, а не в индексе базы

Дата: 2026-09-05 · Статус: принято (владелец) · Заменяет часть ADR-0001
(производная таблица `published_materials_fts` и представление
`pub_search_documents_v1`)

## Контекст

ADR-0001 закрепил FTS5-индекс как часть архитектуры: производная таблица
`published_materials_fts` из представления `pub_search_documents_v1`,
перестройка после каждого применения дельты, проверка чётности при каждом
открытии базы и включение обоих имён в список чтения API.

02.09.2026 поиск переехал в приложение. Владелец проверил поиск за 30 дней по
слову «Яндекс»: три карточки нашлись по скрытому детерминированному описанию, а
на самих карточках стоял текст модели, где этого слова нет. Правило владельца:
поиск работает по тем текстам, которые отображаются. Реализовано это одним
правилом в двух местах — `_card_search_text` в `apps/api/public_data.py` и
`cardSearchText` в `apps/web/app.mjs`: подстрока по всему, что карточка
показывает текстом, включая метку сигнала, хост, дату и рубрики.

Миграция 0003 в тот же день переписала источник индекса под то же правило — под
поиск, который этим индексом уже не пользовался. Ни один запрос API к
`published_materials_fts` не обращается с 02.09.2026.

Измерено 05.09.2026 на продовой базе: индекс — 374 строки, столько же, сколько
в представлении. Он перестраивался при каждой публикации, при каждой миграции и
при каждой проверке базы, а его чётность с представлением сверялась при каждом
открытии базы службой. Несовпадение отвечает 503 на весь сайт.

## Решение

Владелец, 05.09.2026: убрать из контракта.

Миграция 0004 удаляет `published_materials_fts` вместе с её теневыми таблицами
и представление `pub_search_documents_v1`, которое существовало ради неё одной.
Из контракта уходят проверка `fts_rebuild_and_parity`, строка исключения
производных таблиц, оба имени из `apiReadAllowlist` и блок `derivedTables`,
объявленный теперь пустым.

`ENABLE_FTS5` остаётся требованием к рантайму: миграция 0001 создаёт виртуальную
таблицу, и свежая база проходит через её создание, прежде чем 0004 её уберёт.

## Что это меняет в ADR-0001

Разделы про FTS5 в ADR-0001 (архитектура хранения, граница чтения API,
инварианты применения дельты) с этой даты недействительны в части индекса.
Остальное ADR-0001 в силе, включая профиль сборки SQLite с `ENABLE_FTS5`.

## Последствия

Семантика запроса из нескольких слов уточнена решением владельца в
[ADR-0015](0015-search-words-and-reader-recovery.md): каждый фрагмент ищется как
подстрока видимого текста, все фрагменты обязательны, порядок произвольный.

Логическое состояние базы не меняется: индекс в него не входил, поэтому
указатель релиза остаётся верным и дельты продолжают сходиться. Сравнение реплик
упростилось: отдельная сверка индекса существовала потому, что он был
единственной реплицируемой вещью вне хэша логического состояния, — теперь всё,
что читает компаратор, снова внутри дайджеста.

Цена: поиск ищет подстроку, а не слова. «управлен» находит «управления», но
морфологии нет, и на архиве в тысячи материалов линейный проход по тексту
карточек станет заметен. Возвращать поиск в SQL, если это понадобится, значит
собрать оба объекта заново из `issue_materials` и `material_analysis` — ровно
так, как это сделала 0003, — и это будет отдельным решением: правило «ищем ровно
то, что показано» придётся тогда держать в трёх местах вместо двух.

## Почему ADR, а не коммит

Область базы и список чтения API — то, что уже качалось. `GATED_PATHS` за сутки
качнулся свободен → закрыт → свободен, и остановил это ADR-0010, а не чья-то
правка. Индекс, который никто не читает, легко вернуть «на всякий случай»;
запись здесь говорит, что его убрали не по недосмотру.
