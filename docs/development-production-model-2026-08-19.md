# Модель разработки и production-публикации AgPM Radar

Дата фиксации: 2026-08-19

Статус: исторический документ первоначального выделения репозитория. Для реализации использовать согласованный master plan `migration-plan-review-2026-08-19.md`; при расхождении master plan имеет приоритет.

## 1. Решение

AgPM Radar переводится в полноценный режим продуктовой разработки:

- код живёт в отдельном git-репозитории;
- разработка идёт на этом сервере;
- production публикуется на другом сервере;
- во внешний production выносится frontend и весь backend, кроме частей, которые должны оставаться на стороне OpenClaw.

Это не отменяет текущий работающий контур `/mnt/vdd/Radar`. Он становится dev-контуром и исходной точкой для репозитория.

## 2. Границы репозитория

В репозиторий входят:

- frontend-приложение;
- публичный backend API;
- pipeline-скрипты, которые можно запускать без OpenClaw-секретов;
- миграции SQLite;
- healthcheck;
- шаблоны systemd, Caddy/Nginx и deploy-скриптов;
- документация: архитектура, правила выпуска, журнал решений.

В репозиторий не входят:

- SQLite-базы и backup-файлы;
- production- и dev-секреты;
- OpenClaw OAuth-профили и токены;
- логи запусков;
- raw-корпус и служебные кэши;
- временные DOCX/HTML/JSON-артефакты;
- node_modules, build-артефакты и QA-скриншоты.

## 3. Разделение контуров

### Dev-контур

Dev-контур находится на текущем сервере в `/mnt/vdd/Radar`.

Здесь допустимы:

- разработка frontend и backend;
- локальные миграции на dev-копии базы;
- ручные проверки API и UI;
- тестовые публикационные прогоны без воздействия на production;
- обновление документации и регламентов.

### Production-контур

Production-контур находится на отдельном сервере.

Там допустимы только:

- получение release-артефакта из git;
- установка зависимостей;
- применение миграций;
- обновление frontend и backend;
- перезапуск сервисов;
- healthcheck и rollback.

Ручные правки файлов на production не считаются нормальным способом разработки. Если emergency-правка всё же нужна, её нужно сразу вернуть в git как отдельный hotfix.

### OpenClaw-контур

На стороне OpenClaw остаются:

- cron-оркестрация, если выпуск инициируется OpenClaw;
- Telegram-доставка документов и уведомлений;
- вызовы `openclaw infer`;
- OAuth-профили и другие OpenClaw-owned credentials;
- сценарии, где OpenClaw выступает агентным управляющим слоем, а не частью публичного приложения.

Production-сервер не должен хранить OpenClaw-токены. Если production-процессу нужны результаты OpenClaw, он должен получать готовый артефакт или вызывать явно выделенный handoff-механизм.

## 4. Правило публикации

Базовая цепочка выпуска:

```text
dev change
  -> local checks
  -> git commit
  -> release tag
  -> release artifact
  -> production backup
  -> production deploy
  -> migrations
  -> service reload
  -> production healthcheck
  -> release log
```

Запрещено:

- править production напрямую без фиксации в git;
- публиковать изменения из dirty worktree;
- смешивать deploy frontend и миграции базы без rollback-плана;
- хранить секреты в репозитории;
- запускать два независимых daily-планировщика одновременно.

## 5. Минимальный release gate

Перед публикацией на production должны пройти:

- `python3 -m py_compile` для backend и pipeline-скриптов;
- синтаксическая проверка shell-скриптов;
- проверка frontend-скриптов;
- локальный API healthcheck;
- production dry-run или проверка состава release-артефакта;
- резервная копия production-базы;
- production healthcheck после выкладки.

## 6. Ближайшая дорожная карта

1. Инициализировать git-репозиторий в `/mnt/vdd/Radar`.
2. Зафиксировать `.gitignore`, README и этот регламент.
3. Проверить, что git не видит данные, секреты, кэши и backup-файлы.
4. Разделить backend на переносимую часть и OpenClaw adapter.
5. Подготовить production deploy-пакет для отдельного сервера.
6. Описать переменные окружения без значений секретов.
7. Проверить полный цикл на staging-или dev-копии.
8. Только после этого переносить production на отдельный сервер.

## 7. Открытые решения

Нужно отдельно выбрать:

- адрес и доступ к production-серверу;
- способ доставки release-артефакта: git pull, rsync, tarball или CI;
- кто владеет production SQLite и backup-хранилищем;
- остаётся ли OpenClaw cron главным планировщиком daily-выпуска;
- нужен ли отдельный staging между dev и production.
