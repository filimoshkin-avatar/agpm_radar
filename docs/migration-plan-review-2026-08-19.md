# План переезда AgPM Radar на двухконтурную архитектуру

Дата подготовки: 2026-08-19
Статус: документ для ревью другим агентом

## 1. Цель

Нужно перевести AgPM Radar из текущего серверного контура в полноценное приложение с репозиторием, управляемой разработкой и отдельным production-сервером.

Целевая модель:

- доработка функционала идёт на текущем сервере;
- все OpenClaw-операции по сборке ежедневного выпуска остаются на текущем сервере;
- ручное добавление отдельных новостей на следующий выпуск через OpenClaw остаётся на текущем сервере;
- ручные операции по обновлению и восстановлению выпуска остаются в текущем OpenClaw-контуре;
- весь публичный frontend работает с другого сервера;
- на другом сервере находится публичная база с записями выпусков и весь публичный backend, кроме OpenClaw-зависимых частей;
- месячные выпуски «газеты» собираются на текущем сервере по отдельной OpenClaw-команде, проверяются здесь и после проверки публикуются на production-сервер.

## 2. Зафиксированные решения

1. Каноническая база выпусков после публикации остаётся на текущем сервере.

Production-сервер получает полную serving-копию базы опубликованных выпусков. Эта копия используется публичным API, но не редактируется вручную.

2. Передача данных на другой сервер делается через дельты.

Базовый механизм — release tag для кода и SSH/rsync для доставки release-артефактов. Данные выпусков передаются не как ручная правка production SQLite, а как проверенный content delta: миграции, upsert-набор, JSON-cache при необходимости, manifest и контрольные суммы.

3. Очередь ручных новостей «на следующий выпуск» живёт на текущем сервере.

OpenClaw добавляет материалы в локальный управляющий контур. Daily pipeline забирает очередь при следующей сборке. На production попадает только опубликованный результат.

4. LLM-контур на публичном сервере не нужен.

Все LLM-слои формируются на текущем сервере через OpenClaw: краткие тексты карточек, «Что важно для AgPM сегодня», «Аналитический разбор выпуска». Production получает готовые поля в базе и отдаёт их через read-only API.

5. Публичный backend должен быть read-only.

На production нет публичных или скрытых write/admin endpoints для ручного редактирования выпусков. Все изменения проходят через текущий сервер и OpenClaw-контур.

6. Deploy-контур: release tag + SSH/rsync.

Production не должен разрабатываться вручную. На него доставляется проверенный release из git и отдельный content delta для данных.

7. Перестройка каталогов делается поэтапно.

Сначала фиксируется целевая структура и совместимые entrypoints. Затем код переносится из текущих каталогов без остановки daily-контура.

## 3. Целевая архитектура

```text
Текущий сервер
  control plane + dev plane

  OpenClaw
    -> ручное добавление новостей
    -> daily orchestration
    -> LLM через openclaw infer
    -> Telegram-доставка
    -> ручное восстановление и обновление выпусков
    -> команда на сборку месячной газеты

  AgPM Radar repo
    -> разработка
    -> тесты
    -> сборка daily-выпуска
    -> сборка monthly gazette
    -> canonical SQLite
    -> content delta для production

Другой сервер
  public serving plane

  frontend
    -> публичный UI

  backend
    -> read-only API

  production SQLite
    -> serving-копия опубликованных выпусков

  static/public assets
    -> frontend assets
    -> опубликованные страницы месячной газеты
```

## 4. Границы данных

### В git входят

- `backend/` — публичный API-сервер.
- `frontend/` — публичный frontend после поэтапного переноса из `work/radar-app/`.
- `radar/` — переносимая доменная логика радара.
- `pipeline/` — совместимые entrypoints и публикационные команды.
- `adapters/openclaw/` — OpenClaw-зависимые операции.
- `adapters/openai_compatible/` — запасной LLM-контур без OpenClaw, выключенный по умолчанию.
- `config/examples/` — шаблоны без секретов и production-путей.
- `deploy/` — только шаблоны systemd, Caddy/Nginx, deploy-инструкции и скрипты.
- `tests/` — модульные, интеграционные и golden-тесты.
- `fixtures/` — небольшой обезличенный тестовый корпус.
- `docs/` — архитектура, модель данных, правила отбора, эксплуатация, журнал решений.

### В git не входят

- SQLite-базы;
- `materials.jsonl` и `daily-deferred.jsonl`;
- отчёты, DOCX, журналы запусков и результаты ручных прогонов;
- fulltext, raw HTML, сырые ответы Brave, Perplexity и других провайдеров;
- `.bak`, tar-бэкапы, QA-скриншоты;
- OAuth-профили и API-ключи;
- настоящий `radar.env`;
- production cache и экспортированные JSON.

## 6. Daily release flow

### 6.1. Сборка на текущем сервере

1. OpenClaw cron или ручная OpenClaw-команда запускает сбор.
2. Сборщик получает материалы из источников и ручной очереди.
3. Фильтрация применяет правила периметра, отсечения дублей, marketing/agent-wash, проверки ссылок и `fulltext_second_pass`.
4. Выпуск ограничивается максимум 10 материалами.
5. Материалы сверх лимита переносятся в локальную очередь deferred.
6. LLM-слои формируются через `openclaw infer model run --model openai/gpt-5.5`.
7. Локальная canonical SQLite обновляется.
8. Генерируются JSON-cache и служебные артефакты.
9. Выполняется локальный healthcheck.
10. Формируется content delta для production.

### 6.2. Доставка на production

1. Deploy-скрипт создаёт release manifest:
   - дата выпуска;
   - версия git;
   - версия схемы;
   - список таблиц и записей в delta;
   - контрольные суммы;
   - ожидаемые значения healthcheck.
2. Delta доставляется на production по SSH/rsync в каталог incoming.
3. Production делает backup текущей SQLite.
4. Миграции применяются к staging-копии базы.
5. Upsert-дельта применяется к staging-копии в одной транзакции.
6. Проверяются инварианты:
   - выпуск существует;
   - количество публичных карточек совпадает со статистикой;
   - LLM-слои имеют статус `success` или допустимый `skipped` для пустого выпуска;
   - публичный API не отдаёт внутренний список отсечённых материалов;
   - дата публикации материала не подменяется датой выпуска.
7. Staging-копия атомарно заменяет serving SQLite.
8. Backend перезапускается только если изменился код или схема.
9. Выполняется production healthcheck.
10. Результат записывается в release log.

## 7. Monthly gazette release flow

Месячная «газета» — отдельный release-поток, не часть ежедневного автопубликационного цикла.

### 7.1. Сборка

1. Пользователь даёт OpenClaw-команду на сборку отдельного выпуска газеты.
2. Сборка идёт на текущем сервере.
3. Источник данных — canonical SQLite, wiki/compiled-слои и подтверждённые материалы месяца.
4. Генератор формирует HTML-страницу, служебный Markdown-источник и, если нужно, дополнительные assets.
5. OpenClaw/агент проверяет корректность:
   - месяц и период выпуска;
   - полноту материалов;
   - отсутствие черновых или служебных блоков;
   - корректность ссылок;
   - соответствие AgPM-рамке;
   - визуальную пригодность HTML.
6. После проверки формируется gazette release package.

### 7.2. Публикация

1. Газета доставляется на production отдельным deploy-шагом.
2. Production размещает её как статический публичный артефакт.
3. Если страница газеты должна отображаться во frontend, в базу или JSON-cache добавляется запись о выпуске газеты.
4. Production healthcheck проверяет доступность страницы и базовую целостность ссылок.
5. Результат записывается в release log.

### 7.3. Ограничение

Production-сервер не должен сам генерировать месячную газету. Он только публикует проверенный артефакт.

## 8. Ручные операции через OpenClaw

Остаются на текущем сервере:

- добавить отдельную новость на следующий выпуск;
- принудительно перенести материал в deferred;
- исключить материал из выпуска до публикации;
- пересобрать daily-выпуск;
- пересобрать LLM-слои;
- пересобрать месячную газету;
- повторно отправить DOCX/уведомление в Telegram;
- запустить production-deploy после проверки.

Для этих операций нужно добавить явные команды или playbook’и в `adapters/openclaw/` и документацию в `docs/operations-openclaw.md`.

## 9. Этапы переезда

### Этап 0. Зафиксировать модель

- Обновить README и архитектурный регламент.
- Добавить этот план в `docs/`.
- Зафиксировать выбранные развилки.
- Передать документ на ревью другому агенту.

### Этап 1. Подготовить структуру без переноса логики

- Добавить пустые или минимальные каталоги `radar/`, `frontend/`, `adapters/`, `config/examples/`, `tests/`, `fixtures/`.
- Перенести только конфигурационные шаблоны без секретов.
- Добавить `docs/operations-openclaw.md`, `docs/production-serving-plane.md`, `docs/gazette-release-flow.md`.
- Проверить, что текущий daily-контур не изменился.

### Этап 2. Выделить OpenClaw adapter

- Обернуть `openclaw infer` в отдельный adapter.
- Вынести OpenClaw-специфичные команды в `adapters/openclaw/`.
- Оставить совместимый entrypoint для текущего `radar_daily_publish.sh`.
- Проверить выпуск на dev-контуре.

### Этап 3. Подготовить production serving plane

- Выделить read-only API.
- Проверить, что API не зависит от OpenClaw.
- Описать production env без секретов в `config/examples/`.
- Подготовить systemd/Caddy-шаблоны для нового сервера.
- Добавить healthcheck production API.

### Этап 4. Реализовать content delta

- Определить формат delta.
- Добавить manifest.
- Добавить staging-import на production.
- Добавить rollback через backup SQLite.
- Проверить импорт на локальной копии production DB.

### Этап 5. Перенести frontend

- Сначала сохранить совместимость текущего `work/radar-app`.
- Затем перенести frontend в `frontend/radar-app`.
- Обновить deploy-шаблоны.
- Проверить загрузку, API endpoints, cache-busting и доступность assets.

### Этап 6. Включить месячную газету в release-контур

- Выделить генератор газеты в `radar/gazette/` или совместимый pipeline-entrypoint.
- Описать ручную OpenClaw-команду сборки.
- Подготовить package format для production.
- Добавить production healthcheck страницы газеты.

### Этап 7. Первый production cutover

- Подготовить новый сервер.
- Развернуть read-only API и frontend.
- Доставить первую serving-копию базы через delta-процесс.
- Проверить production healthcheck.
- Переключить DNS или reverse proxy после ручного подтверждения.
- Старый публичный контур оставить как rollback до стабилизации.

## 10. Риски

1. Смешение canonical DB и serving DB.

Мера: явно подписать роли баз, запретить ручные write-операции на production.

2. Поломка текущего daily-контура при переносе каталогов.

Мера: переносить поэтапно, сохранять совместимые entrypoints, каждый шаг закрывать healthcheck.

3. Неполная delta на production.

Мера: manifest, staging-import, проверки количества карточек, LLM-слоёв и issue_stats.

4. Утечка секретов в git.

Мера: `config/examples/`, запрет настоящих env-файлов, отдельный secret scan перед release.

5. Газета выпадет из deploy-регламента.

Мера: считать газету отдельным release type с собственным package, проверкой и production healthcheck.

6. Production начнёт зависеть от OpenClaw.

Мера: OpenClaw только на текущем сервере; production получает готовые данные и статические артефакты.

## 11. Что нужно проверить другому агенту

1. Достаточно ли ясно разделены control plane, dev plane и public serving plane.
2. Не противоречит ли delta-подход выбранной роли canonical SQLite.
3. Хватает ли описанных инвариантов для безопасного upsert на production.
4. Нужно ли делать production API только SQLite-based или добавить JSON-cache fallback.
5. Достаточно ли изолирована OpenClaw-зависимость.
6. Корректно ли месячная газета выделена в отдельный release-поток.
7. Какие tests и fixtures нужны до первого cutover.
8. Можно ли первый production cutover сделать без остановки текущего публичного Radar.

## 12. Рекомендуемый ближайший шаг после ревью

Если ревью не выявит архитектурных блокеров, следующий рабочий шаг — выполнить этап 1: добавить целевую структуру каталогов, конфигурационные примеры и операционные документы без переноса логики и без изменения текущего production.
