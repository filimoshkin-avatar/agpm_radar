# Архитектурный план сайта «Радар агентного проектного управления»

Дата фиксации: 2026-07-29

## 1. Зафиксированные решения

1. Сайт `https://radar.aipractice.space/` делаем как живой публичный сервис, а не как статическую витрину.
2. Весь backend, SQLite/API, тяжёлый парсинг, кэш, логи, старые DOCX и рабочие данные проекта размещаем на `/mnt/vdd`.
3. Фронт живёт отдельно в `/mnt/vdd/Radar/work/radar-app`.
4. Экспортёр данных, backfill, LLM-классификатор и рабочие pipeline-скрипты живут в `/mnt/vdd/Radar/pipeline/`.
5. Текущие скрипты радара и старые DOCX можно аккуратно перенести на `/mnt/vdd` с сохранением зависимостей и обратной совместимости.
6. Исторический архив восстанавливаем через парсинг всех старых DOCX. Временные тексты, мусор, ошибки парсинга и промежуточные данные храним на `/mnt/vdd`.
7. Рубрики назначаем через LLM-классификацию только для материалов, которые уже прошли смысловой фильтр.
8. Публично показываем включённые материалы и агрегированную статистику отсечения. Полный список отсечённых материалов остаётся внутренним.
9. Для нумерации выпусков заводим `issue_number` в `state.json`, чтобы номер не зависел от пропущенных дней.
10. Сайт сразу публичный.
11. При backfill старых DOCX нужно ходить по ссылкам на первоисточники, определять реальную дату публикации материала и сохранять материал именно с этой датой. Дата выпуска радара и дата обнаружения остаются отдельными служебными полями.

## 2. Целевая логика сайта

Сайт должен быть публичной витриной ежедневного AgPM-радара. Источник истины — текущий корпус `knowledge/agpm-radar/`, но тяжёлый операционный слой проекта переносится на `/mnt/vdd`.

Сайт показывает не общий поток ИИ-новостей, а отобранный аналитический слой:

- близкий периметр: PMO, проектное и портфельное управление, ИСУП, риски, ресурсы, координация, human-in-the-loop;
- средний периметр: enterprise workflow, governance, безопасность, orchestration, agent gateways, операционные модели;
- дальний периметр: агентные платформы, продукты, MCP, agent workspace, рыночные сигналы;
- статистику шума: сколько просмотрено, сколько включено, сколько отсечено;
- динамику трендов, рубрик, источников и полезного сигнала.

Главный принцип: фронт не читает DOCX, Markdown и журналы запуска. Он работает через API с уже нормализованными данными.

## 3. Текущая база

Сейчас уже есть:

- `knowledge/agpm-radar/data/materials.jsonl` — 4 699 материалов с `id`, `title`, `url`, `published_at`, `summary`, `perimeter`, `source_hits`, `first_seen_at`, `last_seen_at`, `source_count`, `hit_count`;
- `knowledge/agpm-radar/reports/AgPM_daily_radar_YYYY-MM-DD.md|docx` — ежедневные выпуски;
- `knowledge/agpm-radar/runs/YYYY-MM-DD.md` — журналы запуска;
- `knowledge/agpm-radar/wiki/daily/YYYY-MM-DD.md` — дневные wiki-снимки;
- `knowledge/agpm-radar/wiki/stats/overview.md` — агрегаты за 24 часа, 7 дней, 30 дней и месяц;
- `knowledge/agpm-radar/wiki/stats/daily-series.csv` — дневная динамика;
- `knowledge/agpm-radar/wiki/monthly/YYYY-MM.md` — месячные сводки;
- `scripts/agpm_radar_collect.py`, `scripts/agpm_radar_report.py`, `scripts/agpm_radar_wiki.py`, `scripts/agpm_radar_daily.sh`.

Этого достаточно как исходного слоя, но недостаточно для сайта в дизайне. Нужна нормальная база и API.

## 5. База данных и API

SQLite — основной источник данных для сайта. JSON остаётся кэшем и аварийным слоем, но не главным хранилищем.

Базовые таблицы:

- `issues`: дата выпуска, номер, статус, brief, тезисы, ссылки на Markdown/DOCX, время публикации;
- `materials`: URL, источник, реальная дата публикации, дата обнаружения радаром, дата выпуска радара, периметр, статус включения, summary, вывод для AgPM, признак `key`, ссылки на исходные тексты;
- `source_metadata`: URL, заголовок первоисточника, извлечённая дата публикации, способ извлечения, confidence, HTML/текстовый снапшот, ошибка доступа;
- `rubrics`: справочник рубрик;
- `material_rubrics`: связь материалов с рубриками;
- `sources`: источники и статистика полезного сигнала;
- `daily_stats`: просмотрено, включено, отсечено, разбивка по периметрам;
- `llm_classifications`: модель, prompt version, результат, confidence, дата классификации;
- `rejected_materials_internal`: внутренний список отсечённых материалов;
- `pipeline_runs`: запуск, шаги, ошибки, длительность, версия кода.

Минимальный API:

```text
GET /api/health
GET /api/latest
GET /api/issues
GET /api/issues/:date
GET /api/materials?period=day|7d|30d&perimeter=&rubric=&q=
GET /api/stats?period=day|7d|30d
GET /api/timeseries?period=30d
GET /api/rubrics?period=30d
GET /api/sources?period=30d
```

Публичный API не отдаёт полный список отсечённых материалов. Он показывает только агрегаты: количество отсечённых, причины, источники и динамику.

## 6. Что нужно доделать в ежедневных сводках

### 6.1. Структурные поля

Сейчас ежедневный отчёт уже содержит «Суть материала» и «Вывод для AgPM», но это текст в Markdown/DOCX. Для сайта нужно сохранять те же результаты в структуре:

- `summary`;
- `agpm_takeaway`;
- `verdict`;
- `perimeter`;
- `source`;
- `date`;
- `published_at`;
- `first_seen_at`;
- `radar_issue_date`;
- `publication_date_source`;
- `publication_date_confidence`;
- `rubrics`;
- `key`;
- `issue_number`;
- `source_url`;
- `source_id`;
- `classification_status`.

### 6.2. Daily brief и тезисы

Для блока «Что важно для AgPM сегодня» нужен отдельный структурный блок:

- `brief`: 1–2 предложения о повестке дня;
- `theses`: 3–5 тезисов в формате `lead + rest`;
- `trend_notes`: короткие наблюдения о росте или снижении рубрик.

### 6.3. Источники и полезный сигнал

Нужно считать:

- сколько материалов пришло из каждого источника за период;
- сколько прошло смысловой фильтр;
- сколько попало в близкий, средний и дальний периметр;
- долю полезного сигнала;
- вклад AI Agents Directory daily digest отдельно.

### 6.4. Реальная дата публикации

Для сайта нужно различать минимум три даты:

- `published_at` — реальная дата публикации материала в первоисточнике;
- `first_seen_at` — когда материал впервые нашёл радар;
- `radar_issue_date` — в какой ежедневный выпуск радара материал попал.

Календарь архива, тренды по темам и рубрикация по времени должны опираться на `published_at`, а не на дату DOCX-выпуска. Например, если материал попал в июньский DOCX, но на странице первоисточника явно указано 22 февраля 2026 года, в базе и на сайте он должен быть датирован 22 февраля 2026 года. При этом связь с июньским выпуском сохраняется через `radar_issue_date`.

Для каждого материала нужно хранить происхождение даты:

- `url_meta` — дата взята из `article:published_time`, JSON-LD, OpenGraph, RSS или schema.org;
- `page_text` — дата извлечена из видимого текста страницы;
- `docx_context` — дата восстановлена из текста DOCX;
- `fallback_seen_at` — дата публикации не найдена, временно использована дата обнаружения;
- `manual` — дата исправлена вручную.

Если дата не найдена уверенно, материал не надо молча относить к дате выпуска радара. Нужно сохранять низкую уверенность и отдельный статус `publication_date_status = unresolved|low_confidence|resolved`.

## 7. LLM-классификатор рубрик

Классификатор должен работать на русском языке и запускаться только для материалов, прошедших смысловой фильтр.

Рубрики:

- AgPM / PMO / портфели;
- ИСУП и проектная координация;
- Governance и контроль агентов;
- Human-in-the-loop и ответственность;
- Agent workflow и orchestration;
- Безопасность и права доступа;
- MCP, agent gateways и инфраструктура;
- Enterprise adoption и операционные модели;
- Вендоры и продуктовые релизы;
- Исследования и методология;
- Funding / M&A.

Ответ модели должен быть строгим JSON:

```json
{
  "rubrics": ["Governance и контроль агентов"],
  "verdict": "core",
  "confidence": 0.86,
  "explanation_ru": "Материал важен для AgPM, потому что описывает контроль автономных агентов в корпоративной среде.",
  "flags": {
    "governance": true,
    "security": false,
    "human_in_the_loop": true,
    "pmo": false,
    "isup": false,
    "mcp": false
  },
  "key_candidate": true
}
```

Нужно хранить prompt version, модель, сырой ответ, нормализованный ответ и ошибки. Это позволит переиграть классификацию при изменении рубрикатора.

## 8. Исторический backfill DOCX

Нужно парсить все старые DOCX-выпуски, а не только последние 30 дней.

Цепочка:

```text
старые DOCX
  -> /mnt/vdd/Radar/data/corpus/raw-docx/
  -> /mnt/vdd/Radar/data/corpus/parsed-docx/*.txt
  -> переход по ссылкам на первоисточники
  -> извлечение реальной даты публикации
  -> /mnt/vdd/Radar/data/corpus/source-metadata/
  -> normalized-issues/*.json
  -> LLM-классификация рубрик
  -> SQLite
  -> API
```

`materials.jsonl` используется для URL, дат первичного обнаружения, источников, счётчиков и периметра. DOCX нужен для восстановления уже написанных аналитических блоков «Суть материала» и «Вывод для AgPM». Переход по ссылкам нужен для уточнения `published_at`, чтобы старые материалы попадали в правильные календарные даты, а не автоматически наследовали дату выпуска радара.

Если первоисточник недоступен, нужно сохранить ошибку доступа, HTTP-статус, время попытки и fallback-датацию. Такие материалы попадают в очередь повторной проверки.

## 9. Frontend

Рекомендуемая реализация:

- Next.js App Router;
- TypeScript;
- CSS Modules или обычный CSS с дизайн-токенами;
- локальные шрифты из handoff;
- SVG-графики без тяжёлой BI-библиотеки;
- данные через живой API;
- JSON-кэш только как fallback.

Минимальные страницы:

- `/` — главная витрина;
- `/issue/[date]` — полный выпуск дня;
- `/archive` — архив выпусков;
- `/methodology` — методика отбора, если нужна публичная методическая страница.

## 10. Ежедневное обновление

Целевая цепочка:

```text
/mnt/vdd/Radar/pipeline/bin/radar_daily_publish.sh
  -> collect/report/wiki
  -> синхронизация результатов в /mnt/vdd/Radar/data/db/radar.sqlite
  -> LLM-классификация прошедших фильтр материалов
  -> пересчёт агрегатов day/7d/30d/month
  -> обновление JSON-кэша
  -> healthcheck backend/API
  -> фиксация статуса выпуска в pipeline_runs
```

Фронт не нужно пересобирать каждый день, если меняются только данные. Ежедневный pipeline обновляет SQLite и кэш, после чего публичный сайт сразу показывает новый выпуск через API.

Если публикуется новый frontend build, делать это атомарно:

```text
/srv/radar.aipractice.space/releases/2026-07-29-0800/
/srv/radar.aipractice.space/current -> releases/2026-07-29-0800/
```

При ошибке pipeline предыдущий опубликованный выпуск остаётся активным.

Для production лучше оформить запуск через `systemd timer`, потому что он лучше логируется и проще сопровождается, чем разрозненный cron. Локальный `crontab -l` сейчас пуст, поэтому перед внедрением нужно проверить, где фактически запускается текущий ежедневный радар.

## 11. Публичность и внутренний контур

Публично:

- выпуск дня;
- архив выпусков;
- включённые материалы;
- статистика «просмотрено / включено / отсечено»;
- тренды по периметрам, рубрикам и источникам;
- ссылки на первоисточники.

Внутренне:

- полный список отсечённых материалов;
- сырой мусор после парсинга DOCX;
- prompt/response LLM-классификатора;
- ошибки pipeline;
- служебные логи и резервные копии SQLite.

## 13. План работ

### Этап 1. Подготовка данных

- Создать структуру `/mnt/vdd/Radar/data/`.
- Перенести или синхронизировать `knowledge/agpm-radar/`, старые DOCX и рабочие скрипты на `/mnt/vdd`.
- Вынести пути в конфигурацию.
- Подготовить SQLite-миграции.

### Этап 2. Backfill

- Написать `agpm_radar_docx_backfill.py`.
- Извлечь тексты из всех старых DOCX.
- Перейти по ссылкам на первоисточники и извлечь реальные даты публикации.
- Сохранить HTML/текстовые снапшоты первоисточников и источник даты в `source-metadata/`.
- Нормализовать выпуски и карточки.
- Сопоставить карточки с `materials.jsonl`.
- Сохранить ошибки и мусор на `/mnt/vdd`.

### Этап 3. Классификация

- Проработать русскоязычный prompt классификатора.
- Реализовать LLM-классификацию материалов, прошедших фильтр.
- Сохранить результаты, уверенность, объяснение и сырой ответ модели.
- Добавить fallback-правила.

### Этап 4. Backend/API

- Создать backend в `/mnt/vdd/Radar/backend/radar-api`.
- Подключить SQLite.
- Реализовать API.
- Добавить кэш агрегатов и healthcheck.

### Этап 5. Фронт

- Создать Next.js-проект в `/mnt/vdd/Radar/work/radar-app`.
- Перенести дизайн-токены, шрифты, favicon.
- Воссоздать главную страницу по `Радар AgPM.dc.html`.
- Подключить данные из API.

### Этап 6. Публикация

- Настроить backend-сервис.
- Настроить Nginx для `radar.aipractice.space`.
- Подключить TLS.
- Проверить desktop/mobile через Playwright.

### Этап 7. Регулярное обновление

- Собрать `radar_daily_publish.sh`.
- Настроить `systemd timer`.
- Добавить логи, статусы и rollback-поведение.
- Проверить, что новый выпуск появляется на сайте без ручной пересборки фронта.

## 14. Главный вывод

Сайт нужно строить как публичную витрину уже работающего AgPM-радара, но с отдельным живым backend-контуром на `/mnt/vdd`. Главная работа перед фронтом — перенести тяжёлый слой данных на новый диск, восстановить архив DOCX, завести SQLite, API и русскоязычную LLM-классификацию. После этого дизайн из handoff можно реализовывать как интерфейс поверх устойчивой базы, а ежедневный pipeline будет обновлять сайт автоматически.
