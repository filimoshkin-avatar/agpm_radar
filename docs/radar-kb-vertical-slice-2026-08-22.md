# Вертикальный срез 2.1: выборка, gold-наборы и первый замер retrieval

Дата: 2026-08-22. Срез 2.1 плана `docs/radar-v2-kb-engineering-plan-2026-08-22.md` (§13.1), часть
первая: выборка и измеримость. Прогон всех слоёв — после среза 2.0.

Статус: выборка зафиксирована, probe-набор построен и проверен, retrieval измерен на production.
**Планка не назначена** — по P29 её ставит владелец по этим числам, до масштабирования на 275+.

---

## 1. Первый замер

`radar_kx eval-retrieval --gold-set data/eval/vertical-slice-probes-2026-08-22.json --k 10`

| Метрика | Значение |
|---|---|
| Recall@10 | **1,0** (23 из 23) |
| MRR | **0,978** |
| p50 latency | 27 мс |
| p95 latency | 37 мс |

Единственный результат не на первом месте — `boostedcrm.com`: два документа периметра несут
одинаковый текст, и первым выдаётся второй из пары. Это правильное поведение, а не промах.

**Что этот замер измеряет и чего не измеряет.** Probe — дословная фраза из чанка документа. Он
отвечает на вопрос «находит ли индекс текст, который сам же хранит». Он **не** отвечает на вопрос
«понимает ли система заданный человеком вопрос». Второе измеряется набором вида `question`, который
нельзя сгенерировать — его пишут. Отчёт считает два вида раздельно и намеренно не усредняет: одно
число позволило бы отличному probe-результату прикрыть провальный question-результат.

## 2. Как probe-набор чуть не соврал

Первая версия дала Recall@10 = 0,74 и шесть ненайденных probe. Ни один не был отказом поиска. Все
три причины оказались в генераторе фраз, и каждая производит правдоподобный gold-набор, измеряющий
сам себя:

1. **Схлопывание пробелов.** `re.sub(r"\s+", " ", …)` — и фраза перестаёт быть подстрокой документа.
2. **Обрезка на полуслове.** Окно в 260 символов режется по символам; последний «токен» — обрывок,
   который стеммер превращает в лексему, которой в индексе нет.
3. **Пересечение границы чанка.** Фраза есть в документе, но нет ни в одном чанке, а полнотекстовый
   поиск ищет внутри чанка.

`kx/scripts/build_probe_gold_set.py` берёт фразу из **одной строки одного чанка**, по границам слов,
без единого преобразования, и **проверяет её по базе** перед записью. После этого probe, который не
нашёлся, означает ровно то, что написано.

Один документ фразы не даёт и сказано об этом прямо: страница YouTube, где каждая строка — одно-два
слова подвала.

## 3. Выборка: 24 документа, 22 хоста

`radar_kx vertical-slice --candidates candidates.json --size 24`, вход —
`kx/scripts/vertical_slice_candidates.sql`, результат зафиксирован в
`kx/data/eval/vertical-slice-selection-2026-08-22.json`.

План перечисляет свойства, которыми выборка обязана обладать. Выборка «на глаз» удовлетворяет такому
списку случайно, поэтому список сделан кодом: каждое свойство — предикат с минимумом, отбор жадный и
детерминированный, **каждый документ записывает, ради какого требования он взят**, а требование,
которое выполнить нечем, сообщается как пробел.

Размер — цель, а не потолок: покрытие важнее круглого числа, и если требования просят больше
документов, выборка больше и говорит об этом.

Полный текст с Local Ru не уезжает. Извлечение отдаёт хеши — хеш канонического текста и шестнадцать
хешей окон, — а probe-фразы по длине укладываются в цитату.

## 4. Две находки, которых план не ожидал

### 4.1. Перепечаток между изданиями в периметре нет вообще

Ни одна пара документов **с разных хостов** не совпадает даже по двум окнам из шестнадцати.
Требование `cross_host_reprint` сообщено как пробел с нулём доступных.

Это важно: правило независимости источников из ADR-0007 — «одна семья или один дубликат-кластер дают
одно подтверждение» — в вертикальном срезе **проверять не на чем**. Развилка для владельца:

| Вариант | Что даёт | Чего стоит |
|---|---|---|
| Взять пару из корпуса вне периметра | 8 038 неотобранных документов, перепечатка там почти наверняка есть | выборка перестаёт быть подмножеством периметра |
| Ограничиться дубликат-парой `boostedcrm.com` | проверяет `content_duplicate_clusters` | не проверяет `source_families` — а это и есть суть D13 |
| Отложить проверку независимости до 2.4 | честно | нулевой порог §13.1 по независимости в срезе не измеряется |

### 4.2. Девять документов периметра — это подвал YouTube

Девять документов несут один и тот же текст в 215 символов:
«Info / Presse / Urheberrecht / Kontakt … © 2026 Google LLC». Они помечены `is_complete = true` и
входят в те самые «275/275 полных текстов» из отчёта о закрытии.

| | |
|---|---|
| Документов периметра | 275 |
| **Различных текстов** | **266** |
| Документов, дублирующих чужой текст | 11 (9 YouTube + 2 boostedcrm) |
| Complete-версий с неуникальным текстом во всём корпусе | 734 |

`coverage-report` теперь считает `distinct_texts` и `documents_sharing_a_text` по каждому классу
членства, так что число под наблюдением, а не обнаруживается заново.

Один такой документ оставлен в выборке **намеренно** — как случай, на котором ничего не должно
построиться. Остальные исключены из всех прочих требований: подвал сайта английский, короткий,
лежит в каком-то периметре и формально complete, то есть удовлетворил бы половину списка, не измеряя
ничего.

**Что с этим делать — решение владельца.** Варианты: специализированный разбор YouTube (как уже
сделано для Telegram); детектор boilerplate по признаку «текст повторяется у многих документов
одного хоста»; или снятие этих документов с периметра. Гейтом в `coverage-report` это пока не
сделано намеренно — гейт, который падает постоянно, за неделю учит себя игнорировать.

## 5. Что осталось до полного среза 2.1

| Класс проверки §13.1 | Состояние |
|---|---|
| Retrieval (Recall@10, MRR, p95) | **измерено** на probe-наборе; нужен набор вида `question` |
| Доля отказов | нужен строгий режим Q&A — срез 2.14 |
| Extraction / claim binding | нужен срез 2.6 |
| Числа и единицы | нужен верификатор |
| Переводы | нужен срез 2.8 |
| Независимость источников | **нечем проверять**, см. §4.1 |
| Abstention, prompt injection ×2, авторизация | нужны 2.14, 3.2, 3.4 |

Всё перечисленное упирается в срез 2.0 — профиль Hermes и оркестратор, — который требует новых
systemd-юнитов на Local Ru и отдельного подтверждения владельца.

Набор `question` пишется человеком или моделью с проверкой человеком. Сгенерировать его нельзя:
именно в нём и содержится суждение о том, что считается ответом.
