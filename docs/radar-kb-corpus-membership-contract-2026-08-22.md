# Corpus-membership contract

Дата: 2026-08-22. Срез 1.1 плана `docs/radar-v2-kb-engineering-plan-2026-08-22.md` (§6, §6А.4).

Статус: **контракт выполнен по гейту §6.3** — каждое из чисел 284 / 280 / 277 / 275 объяснено
воспроизводимым запросом, а не описанием. Требуется утверждение владельцем.

Контракт отвечает на один вопрос: **что именно мы считаем, когда говорим «материал»**, и по какому
знаменателю будет считаться покрытие. Без него метрики извлечения, разметки и доказательности
несравнимы между собой, потому что каждый слой Radar считает в своих единицах.

---

## 1. Как воспроизвести

Три read-only входа, ни один не пишет в production.

```bash
# 1. Извлечь состояние KX (Local Ru, loopback-only PostgreSQL, транзакция READ ONLY)
sudo -u postgres psql -d radar_kx -X -qAt \
  -f kx/scripts/corpus_membership_kx_extract.sql > kx-extract.json

# 2. Свести все слои и проверить арифметику
python3 kx/scripts/corpus_membership_report.py \
  --legacy-db        /mnt/vdd/Radar/data/db/radar.sqlite \
  --v2-content-root  /var/lib/radar-v2/content \
  --knowledge-root   /root/.openclaw-projectmanager/workspace/knowledge/agpm-radar \
  --kx-extract       kx-extract.json \
  --output           corpus-membership-report.json
```

Отчёт завершается ненулевым кодом, если хотя бы одна проверка не сошлась. Слой KX
необязателен: без `--kx-extract` считаются только файловые и SQLite-слои.

Замер, на котором построен этот документ: релиз `rel_473de6c600563860305e2bd0`
(`releases/ec09152fae33e425e887fd122f18dac8.sqlite`,
sha256 `90495964198e97959907415f68dd28afe1a595edcaaddcd41ae0a4ad9eb7ff8e`), Legacy-база
на 2026-08-22 05:04 UTC, KX schema_version 2.

**Выбранный способ доступа к production** (план требовал зафиксировать его в начале среза):
санкционированный read-only. Legacy открывается `mode=ro` плюс `PRAGMA query_only`, релиз V2 —
`immutable=1`, KX — SQL-файл, целиком обёрнутый в `BEGIN READ ONLY`. Локальная реконструкция
релиза не понадобилась. Копия релизной базы для анализа снята на control-хост; исходник на
Local Ru не изменялся.

## 2. Единицы счёта по слоям

Пять хранилищ, четыре разные единицы. Это не дефект — у слоёв разные задачи, — но переход между
единицами обязан быть явным.

| Слой | Единица | Значение | Источник истины |
|---|---|---|---|
| **Discovery** `agpm-radar/data/materials.jsonl` | запись обнаружения (свой 16-hex id) | **8 446** записей, 8 445 канонических URL | Project Manager |
| **Legacy** `data/db/radar.sqlite` `materials` | строка `(canonical_url, radar_issue_date)` | **284** строки, **280** канонических URL | редакционная база Legacy |
| **V2 release** `materials` | материал релиза | **305** | активный content release |
| **V2 release** `issue_materials` | строка отбора «выпуск × материал» | **277** | активный content release |
| **KX** `issue_perimeter_members` → `documents` | документ = `sha256(normalize_url(canonical_url))` | **275** | KX |
| **KX** `documents` | документ корпуса | **8 313** | KX |
| **Full-text cache** `agpm-radar/data/source-fulltext/` | файл извлечённого текста | **75** (72 с текстом) | Project Manager |

Единица меняется трижды: строка-в-выпуске → материал → документ. Каждый переход ниже.

## 3. Переходы, объяснённые запросом

### 3.1. 284 → 280: строка выпуска против URL

Legacy хранит `UNIQUE(canonical_url, radar_issue_date)`. Один URL, попавший в два выпуска, — две
строки. Таких URL ровно четыре:

| Канонический URL | Выпуски |
|---|---|
| `i2econsulting.com/case-studies/transforming-pmo-daily-standups-with-agentic-ai-project-manager` | 2026-06-08, 2026-06-09 |
| `kiplot.com/knowledge-center/ai-pmo-use-cases` | 2026-06-07, 2026-07-31 |
| `mindstudio.ai/blog/perplexity-computer-vs-openclaw-comparison` | 2026-06-14, 2026-06-17 |
| `ricardo-vargas.com/courses/revolutionizing-project-management-with-ai-agents` | 2026-06-08, 2026-06-09 |

284 − 4 = 280. Проверка `legacy.rows_equal_distinct_urls_plus_repeat_carries`.

**Опровергнуто.** Ходившее объяснение «7 лишних — это `rejected_materials_internal`» неверно:
таблица содержит 7 строк, но ни одна не пересекается с `materials` по URL, и к расхождению
284 → 277 отношения не имеет. Совпадение числа 7 — случайное.

### 3.2. 284 → 277: два разных механизма, а не один

Строк Legacy, которых нет в отборе V2, ровно семь, и они делятся на две несмешиваемые группы.

**Пять — фильтр 30-дневного окна публикации V2.** `v2/tools/build_stage14_daily.py:186-206`:
материал допускается, если дата честно неизвестна (`unresolved` и `published_at IS NULL`) либо
разрешённая дата лежит в `[issue_date − 30 дней, issue_date]`. Всё остальное отклоняется.

| Выпуск | `published_at` | Окно | URL |
|---|---|---|---|
| 2026-08-20 | 2024-10-29 | 2026-07-21…08-20 | `automationanywhere.com/rpa/agentic-workflows` |
| 2026-08-21 | 2026-04-02 | 2026-07-22…08-21 | `labs.cloudsecurityalliance.org/research/csa-research-note-nist-ai-agent-standards-initiative-2026040` |
| 2026-08-21 | 2026-04-25 | 2026-07-22…08-21 | `beri.net/article/agentic-ai-roi-171-percent-enterprise-case-studies` |
| 2026-08-22 | 2026-06-01 | 2026-07-23…08-22 | `msagilemed.com/ai-agentic-workflows-for-product-owners` |
| 2026-08-22 | 2026-06-11 | 2026-07-23…08-22 | `quire.io/blog/p/what-is-agentic-project-management.html` |

Все пять — из трёх последних выпусков, то есть из тех дней, которые V2 собирал сам в режиме
dual-run. Ни одного такого расхождения на исторических выпусках нет: bootstrap-импорт окно не
применял.

**Два — зафиксированная редакционная коррекция.** Выпуск 2026-06-09 нёс два URL, уже вышедших
2026-06-08. Коррекция `cand_stage14_historical_dedup_20260609_04`
(релиз `rel_24323825419982d88e885829`, `operation='correction'`), исправленная
`cand_stage14_historical_dedup_repair_20260609_01`, сняла повторы; количество материалов выпуска
изменилось с 12 на 10. Записано в `docs/radar-stage14-project-manager-dry-runs-2026-08-20.md`.

284 − 5 − 2 = 277. Проверка `legacy_to_v2.every_dropped_row_is_explained` требует нуля строк, не
попавших ни в одну из двух групп. Обратное направление закрыто проверкой
`legacy_to_v2.v2_publishes_nothing_legacy_never_saw`: отбор V2, которому нет строки в Legacy,
никаким фильтром V2 объяснить нельзя и всегда означает дефект. Сейчас таких ноль.

### 3.3. 305 → 277: релиз шире отбора

`materials` релиза — не отбор. 305 материалов раскладываются по способу попадания в релиз, и
способ восстанавливается из идентификатора: bootstrap хеширует ключ в
`mat_<sha256("radar-v2:material:<ключ>")[:24]>` (`v2/packages/legacy_bridge/importer.py:170`).

| Происхождение | Ключ хеширования | Количество |
|---|---|---|
| Материал Legacy | `<legacy id>` | **279** |
| Строка `source_metadata` Legacy без совпавшего материала | `source-metadata:<url>` | **24** |
| Дневная очередь отложенных | запись `editorial_queue` со `state='deferred'` | **2** |

279 = 277 отобранных + 2 снятых коррекцией 2026-06-09. Остальные 26 в выпуски не входили никогда.

Отложенные атрибутируются по строке очереди в самом релизе, а не по ключу: ключ содержит id из
`daily-deferred.jsonl`, который Project Manager переписывает на месте, поэтому исторического
значения ключа уже не существует. Строка `editorial_queue` — единственное долговечное
свидетельство этого пути. Проверка `v2.materials_are_fully_attributed` требует, чтобы
неатрибутированных материалов было ноль.

### 3.4. 277 → 275: строка отбора против документа

KX ключует документ как `sha256(normalize_url(canonical_url))`, поэтому один URL, отобранный в два
выпуска, — один документ. В текущем отборе таких URL два:
`mindstudio.ai/blog/perplexity-computer-vs-openclaw-comparison` (2026-06-14 и 2026-06-17) и
`kiplot.com/knowledge-center/ai-pmo-use-cases` (2026-06-07 и 2026-07-31).

277 − 2 = 275. Проверяется не только мощностью множества, но и симметрической разностью
(`kx.perimeter_document_ids_are_reproducible_from_the_release`): равные числа на разных документах
иначе прошли бы молча.

Полный текст: **275 из 275** документов периметра имеют complete-версию
(`kx.perimeter_full_text_is_complete`).

### 3.5. 8 313 документов KX

| Источник документа | Количество |
|---|---|
| Импорт корпуса `materials.jsonl` (`material_documents`) | 8 308 |
| Создан напрямую импортом периметра, материала нет | 5 |

8 308 + 5 = 8 313 (`kx.documents_reconcile_with_materials`). Пять документов без материала:

| URL | В текущем периметре |
|---|---|
| `arxiv.org/abs/2608.10218` | да |
| `finam.ru/publications/item/budushchee-uoll-strit-…-20260801-1152` | да |
| `gartner.com/en/newsroom/press-releases/2025-08-17-gartner-says-shared-chro-cio-ownership-…` | да |
| `pmpractice.ru/news/2026/8445` | нет |
| `meta.com/thefutureisforeveryone` | нет |

Первые три — те же три URL, которых нет в discovery-реестре (§4.1): материал добавлен редакционно,
минуя дневной обход, поэтому в KX он попал только через импорт периметра. Два оставшихся —
следствие того, что `materials.jsonl` переписывается на месте: их записи были в импорте
`radar-corpus-7653-eb4c51b11e85` и исчезли из файла к импорту `radar-corpus-8310-b17bc175f9ac`
(`materials.jsonl.bak.before-pmpractice-link-fix-…`,
`materials.jsonl.bak.before-meta-future-everyone-…`). Документы KX immutable и остались.

**Это и есть содержательная причина, по которой P28 обязателен**: файловый реестр изменяем, KX —
нет, поэтому расхождение накапливается молча и обнаруживается только сверкой.

## 4. Файловые хранилища

### 4.1. Discovery-реестр

`agpm-radar/data/materials.jsonl` — 8 446 записей в собственном 16-hex пространстве
идентификаторов, **не совпадающем** с `materials.id` Legacy: пересечение по id пустое. Единственный
общий ключ между реестром и Legacy — канонический URL.

- перимeтр: `watch` 4 708, `far` 2 413, `middle` 1 044, `near` 281;
- один повторяющийся канонический URL: `pmpractice.ru/news/8424`;
- 277 из 280 канонических URL Legacy присутствуют в реестре; отсутствуют три —
  `arxiv.org/abs/2608.10218`, `finam.ru/publications/item/budushchee-uoll-strit-…`,
  `gartner.com/en/newsroom/press-releases/2025-08-17-…`;
- **136 записей добавлены после снимка, который импортирован в KX** (8 446 против 8 310).

Обратите внимание на асимметрию единиц: реестр называет `perimeter` значением `middle`, схема V2
и радарная wiki — `mid`. Отображение однозначно, но при сравнении обязано быть явным.

### 4.2. Кэш полных текстов

`agpm-radar/data/source-fulltext/` — 75 файлов, имя файла = `sha256(canonical_url)[:24]`. Поскольку
`normalize_url` на этой популяции ничего не меняет (§5), **имя файла является префиксом
`document_id` в KX** — два хранилища уже разделяют вывод ключа, таблица соответствия не нужна.
Проверка `fulltext.file_names_match_their_canonical_url`.

Статусы: `resolved` 72, `unresolved` 2, `unsupported_content_type` 1.

**Пять файлов не подтверждены в KX** — рабочая копия Project Manager содержит текст, которого нет в
доказательной базе:

| Канонический URL | Есть документ в KX | Символов в файле |
|---|---|---|
| `augmentedpm.co.uk/insights/agentic-project-management-overhyped` | нет | 5 593 |
| `ecorpit.com/engineering-lessons-shipping-enterprise-ai-agents-2026` | нет | 15 734 |
| `institutepm.com/knowledge-hub/ai-agent-workforce-integration-2026` | нет | 13 419 |
| `linkedin.com/posts/bailing-zhang-…-activity-7465414252422590464-t-To` | да, без complete-версии | 20 000 |
| `appian.com/learn/topics/enterprise-ai/ai-agent-use-cases` | да, без complete-версии | 16 026 |

Последняя строка — **не** документ Appian из периметра (D9): периметр содержит
`appian.com/blog/pm/building-enterprise-grade-ai-agents`, и он complete. Совпадение домена
обманчиво, поэтому сверка ведётся по URL, а не по хосту.

## 5. Канонизация URL и дедупликация

Две нормализации, и они **не одна и та же функция**.

| | Legacy | KX (`kx/src/radar_kx/url_policy.py:normalize_url`) |
|---|---|---|
| `www.` | снимается | **сохраняется** |
| завершающий `/` | снимается | **добавляется**, если путь пуст |
| регистр хоста | нижний | нижний, плюс IDNA |
| порт по умолчанию | — | снимается |
| `utm_*`, `fbclid`, `gclid`, `ref`, `source`, `yclid`, `ysclid`, `mc_cid`, `mc_eid`, `ref_src` | — | снимаются |
| схема не `http(s)` | допускается в поле | отвергается `UnsafeUrlError` |

KX применяется **после** Legacy: в манифест и в экспорт периметра попадает уже канонизированный
Legacy URL, и `normalize_url` его дополнительно нормализует. На текущей популяции из 280 URL это
**no-op**: ни один URL не переписан и ни один не отвергнут
(`normalization.kx_does_not_rewrite_legacy_canonical_urls`).

Это наблюдаемое свойство популяции, а не инвариант. Правило контракта:

> Канонический URL — единственный ключ соединения между всеми пятью хранилищами. Как только
> `normalize_url` начнёт что-то переписывать, счётчики слоёв станут несравнимы. Проверка
> обязана оставаться в гейте и обязана падать, а не предупреждать.

**Дедупликация.** На уровне membership дедупликация ровно одна: по нормализованному каноническому
URL. Содержательные дубликаты (перепечатки, синдикация, общий пресс-релиз) к этому контракту не
относятся — это `content_duplicate_clusters` и `source_families` из §10.4 плана, отдельная модель
с отдельным решением.

## 6. Текущий и исторический периметр (D3)

`issue_perimeter_members` хранит по строке на снимок; снимков сейчас два.

| Снимок | Захвачен | Строк | Документов |
|---|---|---|---|
| `v2_content_release:rel_1c420e848b99357be9b53106` | 2026-08-21 18:17:58Z | 269 | 267 |
| `v2_content_release:rel_473de6c600563860305e2bd0` | 2026-08-22 06:16:47Z | **277** | **275** |

Union по обоим снимкам — тоже 275: из старого снимка не выбыло ничего, добавилось 8. Поэтому
дефект D3 (view `issue_perimeter_documents` не фильтрует по `perimeter_source_id`) остаётся
**латентным**: сегодня union и текущий периметр совпадают численно и поимённо.

Правила контракта:

1. **Текущий периметр** — документы последнего по `captured_at` снимка. Это знаменатель по
   умолчанию для любой метрики покрытия.
2. **Исторический периметр** — union всех снимков. Используется только там, где вопрос явно про
   историю.
3. **Любой отчёт обязан называть, какой из двух он показывает.** Отчёт без этого указания
   недействителен: сегодня числа совпадают, и ошибка не проявится до первой коррекции, снимающей
   материал с опубликованного выпуска.
4. До исправления D3 view `issue_perimeter_documents` показывает **исторический** периметр, как бы
   он ни назывался. Запрос текущего периметра пишется через `issue_perimeter_members` с явным
   `perimeter_source_id`.

## 7. Источник истины по вопросам

| Вопрос | Отвечает | Не отвечает |
|---|---|---|
| Сколько материалов в выпуске | V2 `issue_materials` активного релиза | Legacy: у него своя редакционная строка на дату |
| Что вообще было обнаружено | discovery-реестр `materials.jsonl` | KX: он содержит только импортированный снимок |
| Есть ли полный текст и какой именно | KX `document_versions` | файловый кэш: это рабочая копия |
| Что размечено и как | слой таксономии (после 2.5в) | текущие `material_rubrics`: разметка сделана fallback-правилами (§4 плана, R1) |
| Чем подтверждено утверждение | KX `claim_evidence` | wiki: она утверждает, но не доказывает |
| Какой текст авторский | файловая wiki `knowledge/agpm/` | KX |

**При расхождении для доказательств истина — KX, всегда** (это же правило закрепляется в ADR-0008).

## 8. Что размечается и что оценивается

Развилка §6.2.5 плана закрывается так:

| Работа | Знаменатель | Почему |
|---|---|---|
| Переразметка (тема / периметр / жанр), извлечение claims, полный текст, доказательства, оценка источникового уровня | **275 документов текущего периметра** | Единица работы — документ. Дважды отобранный URL — один текст, размечать его дважды бессмысленно, а считать покрытие по 277 значило бы считать один документ за два |
| Редакционные метрики выпусков: «сколько материалов вышло», «как распределены по периметрам», лента и сводки | **277 строк отбора** | Единица работы — публикация в выпуске. Материал, вышедший дважды, — два редакционных события |
| Сверка Legacy ↔ V2 в dual-run | **284 строки Legacy** | Смысл сверки в том, чтобы увидеть расхождение контуров; приведение к общему знаменателю его бы скрыло |
| Метрики обнаружения (охват дальнего периметра, доля отобранного) | **8 446 записей реестра** | — |

Число 280 не является знаменателем ни для чего. Это промежуточная величина, полезная только при
разборе перехода 284 → 277.

**Оценка материала (P22) относится к документу**, а не к строке отбора: `material_scores` ключуются
`document_id`. Иначе один текст получил бы две несовпадающие оценки за два появления, и владельцу
пришлось бы решать, какая из них настоящая.

## 9. Классы членства

Периметр выпусков — не единственный класс. Контракт фиксирует четыре, чтобы каждый имел
собственный знаменатель и не смешивался с остальными.

| Класс | Что входит | Знаменатель покрытия | Отношение к периметру |
|---|---|---|---|
| **`issue_perimeter`** | документы, отобранные в опубликованные выпуски | 275 (текущий снимок) | это он и есть |
| **`corpus`** | всё, что импортировано из discovery-реестра | 8 313 документов KX | надмножество |
| **`canon_import`** (срез 1.6, P25) | канон AgPM и внешние стандарты из `agpm/raw/*.md` | считается отдельно, по числу загруженных документов канона | **не пересекается** и **не входит** в знаменатели покрытия по материалам радара |
| **`operator_artifact`** | документы, переданные оператором файлом | входит в свой класс, учитывается в провенансе | может пересекаться с `issue_perimeter` |

Правило для канона: строка `corpus_imports` с собственным `source_name` и
`source_kind = 'canon_import'`; синтетический канонический URL `agpm-canon:/<путь-в-raw>`, схема
не пересекается с `http(s)` и потому **отвергается** `normalize_url`. Отсюда следствие, которое
надо учесть в 1.3: `document_id` для канона вычисляется по синтетическому URL напрямую, минуя
`normalize_url`, и это обязано быть явной веткой в коде, а не побочным эффектом.

Покрытие никогда не считается по объединению классов. «Покрыто 90 %» без имени класса —
недействительное утверждение.

## 10. Роль файлового хранилища и KX (P28, принято, не пересматривается)

Решение владельца P28 переносится в контракт как есть:

- `agpm-radar/data/source-fulltext/` — **рабочая копия** Project Manager;
- KX — **доказательная база** публикации;
- расхождение неизбежно и обязано быть видимым: регулярный отчёт сверки (срез 2.4а,
  таблица `store_reconciliation_reports` из миграции 003).

Отчёт §4.2 — первый прогон этой сверки. Он уже нашёл 5 расхождений на 75 файлах и 136 записей
реестра, не дошедших до KX. Ни одно из них не является ошибкой само по себе; ошибкой было бы
узнать о них в момент, когда они сломают публикацию.

**Направление синхронизации — одностороннее**: файловый контур со временем читает тексты из KX
через research API; собственный сбор не расширяется. Обратной записи из KX в `knowledge/` нет.

## 11. Гейт

Контракт считается соблюдённым, пока `corpus_membership_report.py` завершается нулевым кодом.
Тринадцать проверок на замере 2026-08-22, все зелёные:

| Проверка | Смысл |
|---|---|
| `legacy.rows_equal_distinct_urls_plus_repeat_carries` | 284 = 280 + повторные выносы |
| `legacy.ids_are_unique` | иначе вывод идентификатора V2 схлопнется |
| `v2.materials_are_fully_attributed` | 305 материалов релиза объяснены входами |
| `legacy_to_v2.every_dropped_row_is_explained` | каждая потерянная строка — окно или коррекция |
| `legacy_to_v2.v2_publishes_nothing_legacy_never_saw` | обратное направление, всегда ноль |
| `normalization.kx_does_not_rewrite_legacy_canonical_urls` | ключ соединения един для всех хранилищ |
| `kx.current_snapshot_matches_the_active_release_selection` | снимок не устарел |
| `kx.perimeter_documents_are_the_selection_deduplicated_by_url` | 275 = 277 − 2 |
| `kx.perimeter_document_ids_are_reproducible_from_the_release` | симметрическая разность, не только мощность |
| `kx.perimeter_full_text_is_complete` | 275/275 |
| `kx.documents_reconcile_with_materials` | 8 313 = 8 308 + 5 |
| `discovery.ids_are_unique` | реестр ключуется по id |
| `fulltext.file_names_match_their_canonical_url` | иначе сверка молча пропустит файл |

Числа периметра и корпуса растут ежедневно, поэтому гейт проверяет **арифметику разложения**, а не
конкретные значения. Абсолютные числа этого документа — замер, а не константа.
