# ADR-0020: событийная дедупликация в production работает как наблюдение

> Аудитория исправлена в [ADR-0021](adr-0021-owner-only-event-observations.md): отчёты доступны только в закрытом разделе продакт-оунера `/po/`. Публичный endpoint удалён.

Дата: 2026-09-19. Статус: принято по прямому запросу владельца.
Заменяет блокирующую production-политику ADR-0019 до отдельного решения после калибровки.

Независимое извлечение паспортов и совместные LLM-разборы пока нестабильны:
границы событий, даты и принадлежность фактов меняются между запусками. Нельзя
автоматически менять выпуск или блокировать его на основании этих гипотез.

## Решение

- `PRODUCTION_MODE = observe` — одна общая политика Legacy и V2. Сохраняются
  запреты повторного ID/канонического URL/рендера. Семантическое объединение,
  удаление, перефокусировка обзоров, историческое подавление и обязательные
  паспорта отключены. Старый строгий алгоритм остаётся для экспериментов.
- После успешной публикации/повтора Stage15 запускает отдельный процесс.
  Модель и загрузка отчёта не влияют на результат публикации. Используется
  существующий планировщик; новых systemd-юнитов и миграций production нет.
- Проверяем действительный опубликованный фокус карточек: заголовок, видимое
  описание, видимый вывод. Успешные LLM-тексты имеют тот же приоритет, что в UI
  и поиске. Сырые статьи и второстепенные упоминания в обзоре не считаются
  ранее опубликованными событиями. Полнотекстовая проверка пока отсутствует;
  недостаток данных — отдельный результат, а не доказательство различия.
- Все пары внутри выпуска плюс TF-IDF-кандидаты из 45 дней истории: до пяти
  на карточку с cosine >= 0.12 либо общей именованной латинской сущностью
  (Anthropic, Claude и т. п.; общие термины исключены). Это поисковые настройки, не пороги слияния;
  recall ещё не измерен. Не более 100 пар в отчёте, по 6 в вызове, 10 новых
  вызовов / 480 секунд между вызовами на проход, timeout вызова 120 секунд.
  До трёх проходов с точным кешем; частичный/ошибочный результат явно помечен.
  Каждый следующий daily-запуск также возобновляет до двух старых незавершённых
  или не доставленных отчётов за 45 дней.
- JSON привязан к хешу полного публичного DTO выпуска; каждая пара — к хешам
  видимых текстов. Версии модели/промпта, охват, ошибки и все решения сохраняются.
  Фрагменты доказательств проверяются как точные подстроки опубликованного фокуса.
  Уверенность — самооценка модели, не откалиброванная вероятность дубля.
- Ограниченный SSH-активатор принимает отдельное действие `event_observation`,
  проверяет опубликованный DTO и сохраняет артефакт под фиксированным корнем.
  Никаких изменений БД/указателей выпусков. У отчётов собственная блокировка,
  независимая от блокировки публикации. API имеет только чтение.
- `GET /api/event-observations/{issueDate}` возвращает отчёт только для текущей
  версии выпуска. Фронт сверяет его с `X-Radar-Issue-Hash` загруженного выпуска;
  при несовпадении предлагает обновить страницу. Ошибка не выглядит как ноль дублей.
- Публичны только гипотезы по уже публичным карточкам. Редакторские метки приватны:
  UI сохраняет черновик в браузере и экспортирует JSON, оператор импортирует его
  в отдельный неизменяемый журнал с указанием редактора. Отсутствие серверного
  сохранения в UI обозначено явно; не создаём публичный endpoint для записи.

## Эксплуатация

Команда повтора и импорта меток описана в `v2/docs/event-observation-operations.md`.
После адресной коррекции выпуска вне daily-контура оператор запускает наблюдение
для новой версии. Старый отчёт остаётся архивным и не показывается для новых карточек.
Включение автоматических объединений требует отдельного решения владельца и
измеренной калибровки на редакторской разметке, а не появления файла допуска.
