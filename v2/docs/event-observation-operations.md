# Наблюдение за повторами в production V2

Политика: [ADR-0020](adr-0020-event-observation-calibration.md), аудитория —
[ADR-0021](adr-0021-owner-only-event-observations.md).
Редакторская коррекция и уведомления: [ADR-0022](adr-0022-owner-composition-review.md).
Отчёты находятся только в [разделе продакт-оунера](https://radar.agpm.space/po/#event-observations),
вкладка «Повторы выпусков», после входа. Публичные выпуски панели не содержат. Состав карточек
автоматически не меняется по отчёту; коррекция требует отдельного подтверждения
владельца. Ошибка модели/транспорта сохраняется
как ошибка/частичное покрытие либо недоступность отчёта; это не «дублей нет».

Daily Stage15 автоматически запускает worker после публикации, включая повтор
готового `combined-report.json`. Worker выполняет до трёх проходов, использует
точный кеш успешных пакетов и блокировку на дату. Следующий daily-запуск также
подхватывает до двух старых незавершённых/недоставленных отчётов за 45 дней.
Модель не запускается в API и не требует нового systemd-юнита.

## Повтор / новая версия после коррекции

На контрольном хосте из `/mnt/vdd/Radar/v2`:

```bash
.venv/bin/python -m tools.observe_issue_events \
  --issue-date 2026-09-19 \
  --source-root /root/.openclaw-projectmanager/workspace/state/radar-v2/source \
  --root /root/.openclaw-projectmanager/workspace/state/radar-v2/dual-run-cron/event-observations
```

Дата — нужный опубликованный выпуск. Это обязательный шаг после коррекции вне
Stage15. Успешный отчёт текущей модели/промпта повторно доставляется без LLM;
смена модели/промпта или хеша карточек создаёт новый анализ.

Локальный корень хранит `reports/<reportId>.json`, кеш, журналы `<date>.log`,
`receipts/` подтверждений доставки и `labels/` редакторских решений. Серверный
корень `/var/lib/radar-v2/event-observations` содержит архивные отчёты и текущий
отчёт под `<issueHash>.json`; владелец `radar-v2-api`, каталог 0700, файлы 0600.
Запись выполняет только ограниченный активатор. Endpoint не раскрывает raw cache.

## Калибровка

1. Открыть подозрительные пары и при необходимости «Остальные проверенные пары».
2. Выбрать «Дубль», «Разные события», «Развитие» или «Недостаточно данных».
   Оценки неизменившихся пар сохраняются при переходе от частичного к полному
   отчёту: пара привязана к хешам обоих видимых текстов.
3. Нажать «Скачать разметку». Пока это локальный черновик браузера, не общая БД.
4. Передать файл оператору, который импортирует его с именем редактора:

```bash
.venv/bin/python -m tools.observe_issue_events \
  --root /root/.openclaw-projectmanager/workspace/state/radar-v2/dual-run-cron/event-observations \
  --import-labels /path/to/radar-2026-09-19-event-labels.json \
  --reviewer editor-name
```

Импорт проверяет report ID, принадлежность каждой пары и допустимые метки.
Он добавляет новую запись; исходный ответ модели и прежние метки не изменяются.
Исправленные оценки сохраняются новой записью, при анализе используют последнюю
оценку данного редактора для пары. Уверенность модели не является same-event score:
например, высокая уверенность в `different_event` означает уверенность в различии.

## Пересмотр состава

После выбора редакторской оценки появляется список карточек выпуска. Для оценки
«Дубль» можно снять отметку «Оставить» с карточки текущего выпуска, открыть
предпросмотр и нажать «Подтвердить и опубликовать состав». Только это подтверждение
сохраняет серверную заявку вместе с оценками и автором. Оценка сама по себе
ничего не исключает. Нельзя удалить карточки других выпусков, весь выпуск или
две карточки одной подтверждённой пары.

OpenClaw `agpm_radar_v2_owner_corrections` проверяет заявки каждые две минуты
через `tools.process_issue_reviews`. Статус виден в редакторе, в том числе после
перезагрузки страницы. Пересборка анализа может занять несколько минут.
Новая версия проходит обычную публикацию V2 и повторное наблюдение. Устаревшая
оценка отклоняется; транспортный сбой повторяется с тем же пакетом. После трёх
неудачных пересборок можно подтвердить заявку повторно для прежней версии.

Серверные заявки: `/var/lib/radar-kx/issue-reviews/<reviewId>.json`.
Пакеты и результаты на контрольном хосте:
`/root/.openclaw-projectmanager/workspace/state/radar-v2/issue-reviews/<reviewId>/`.
Не удалять сохранённые пакеты при неопределённом результате публикации:
повтор штатного публикатора восстанавливает также локальный указатель.

## Ежедневное уведомление

Daily-отчёт содержит `eventObservation`: состояние проверки, охват, число
подозрительных пар и ссылку на дату в `/po/`. Если проверка ещё идёт, это явно
указано; готовый результат приходит отдельным дополнением в тот же настроенный
канал OpenClaw. Квитанции доставки находятся в `event-observations/notifications`.
Следующий daily повторяет доставку недоставленных результатов в пределах
существующего лимита обработки двух старых отчётов за запуск.

Первый этап использует только опубликованный видимый текст, без полного текста
источников. Поиск истории ограничен пятью кандидатами на материал. Сначала измеряем
ошибки решений и отдельно пропуски поиска; наличие зелёного отчёта не доказывает
отсутствия всех событийных повторов.

## Выкат / откат

Развёртываются API/web, ограниченный activator (включая новые contract/storage/
publisher модули) и зеркало `pipeline/scripts/agpm_radar_report.py` на контрол-хосте.
Не менять `scripts/run_stage15_daily.sh`. Контрольные хеши публичных DTO всех выпусков
должны совпасть до/после. Прежние указатели API/web/activator сохраняются для отката.
При откате прежнего приложения нужно учитывать, что оно возвращает блокирующую
семантическую политику; это не способ отключить лишь отображение отчёта.

## Доступ PO к отчётам

Редактор проверяет действующий вход на каждом запросе и обращается к V2 с
серверным bearer. `/etc/radar-v2/owner-observations.token` — копия bearer из
`/etc/radar-kx/editor.env`, владелец radar-v2-api, mode 0400. При ротации токена
редактора копию необходимо обновить; браузеру она не выдаётся.
После выката KX обязательно перезапустить `radar-kx-editor`; его PAGE/SCRIPT
загружаются при старте. Старый публичный endpoint отвечает 404.
